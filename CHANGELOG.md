## [Unreleased]

### Fixed
- **Deleting a normalization rule group left a dangling reference in auto-creation rules that then refused to save (GH #465, bd-miut3, build 0004).** An auto-creation rule stores the normalization rule groups it applies as `normalization_group_ids` (the "Normalization Groups" selector in the rule editor — the groups that strip quality tags). `DELETE /api/normalization/groups/{id}` removed the group and its rules but never stripped that id from any rule's `normalization_group_ids`, so the rule kept a reference to a group that no longer existed. On the next edit the rule editor reloaded the full id list but couldn't render a checkbox for the missing group, and the write-time validator (`_validate_normalization_group_ids`, bd-i75ax) then rejected every save with `422 — normalization_group_ids do not exist`; the only workaround was "Clear all + re-select". **Impact was save-block only** — at run time `normalize(group_ids=…)` filters by membership, so a missing id was silently ignored and auto-creation still ran correctly. Fix: deleting a normalization group now cascade-strips its id from every auto-creation rule's `normalization_group_ids` in the same transaction (`_strip_normalization_group_ref`), and a startup heal (`_heal_orphaned_normalization_group_refs`, in `_run_migrations`) repairs rules orphaned by deletions that happened before this fix shipped — so already-broken rules become saveable again without operator action. (GH #465, bd-miut3, build 0004)
- **Scheduled tasks showed "Next Run: Never" in Settings → Scheduled Tasks despite having an active schedule (GH #468, bd-a80u2, build 0003).** The "Next Run" the UI renders came from the registry's in-memory `instance._next_run`, which is loaded from the DB only once at startup (`sync_from_database`). Every path that maintains schedules — the schedule create/update/delete endpoints (`_update_task_next_run`) and `task_engine.check_and_run_tasks` after a run — updates the **database** (`scheduled_tasks.next_run_at` + `task_schedules.next_run_at`) but never refreshes the in-memory instance. Tasks whose default schedule is `MANUAL` (Stream Probe, Re-probe Failed Streams, EPG/M3U refresh, etc.) start with `instance._next_run = None`, so adding a schedule through the multi-schedule UI left the in-memory value at `None` and the UI showed "Never" until the next container restart. Compounding this, `_save_task_to_db` wrote the stale in-memory `None` back over the correctly-computed `scheduled_tasks.next_run_at`, so any later `sync_to_database` (e.g. editing alert settings) clobbered the DB value and made "Never" persist across restarts. **Impact was display-only** — the task engine fires off the child `task_schedules.next_run_at` rows, which were always correct, so the tasks did run on schedule. Fix: `GET /api/tasks` and `GET /api/tasks/{id}` now source "Next Run" from the earliest enabled `task_schedules.next_run_at` (the real firing source) instead of the stale in-memory value, falling back to the in-memory value only for tasks with no schedule rows; and `_save_task_to_db` no longer overwrites `next_run_at` for tasks that have `task_schedules` rows (those are DB-managed). (GH #468, bd-a80u2, build 0003)
- **Bulk channel creation re-paginated the entire Dispatcharr logo catalog once *per channel*, making large batches O(channels × catalog-pages) and exhausting the request budget (bd-raehx, build 0002).** Every `createChannel` op carrying a `logoUrl` but no `logoId` called `find_logo_by_url()`, which paginates the whole logo catalog (500/page) on every call with no caching. Two real debug bundles confirm the cost: a 441-op SiriusXM batch issued **2,391** logo GETs (~5-page catalog, finished server-side in ~6 min after a 504), and a 113-op batch against a larger ~25-page catalog issued **859** logo GETs and reached only ~channel 22 before the 30s `504`. This is why batches "created channels but didn't assign streams past ~15", why an op reported *failed* while the write still happened (the handler keeps running after the client's 504), and why adding streams manually afterward worked. Fix: `_run_bulk_commit` now builds a per-run `{url → logo}` index **once**, lazily (only the first time an op actually needs a logo lookup, so `validateOnly` and logo-free batches pay nothing), and every subsequent op reuses it; logos created mid-batch are inserted into the index so a later op sharing the same `logoUrl` reuses them instead of creating a duplicate (also fixes a latent duplicate-logo bug). Catalog fetches drop from ~859/2,391 to ~25/5 — one pagination per batch. The per-channel `find_logo_by_url` first-match semantics and the "logo failure still creates the channel without a logo" fallthrough are preserved. (bd-raehx, build 0002)
- **Bulk-commit partial outcomes are now flagged explicitly so the client can distinguish "some applied, some failed" from a total failure (bd-5xciq, build 0002).** The `BulkCommitResponse` envelope gains a `partial` boolean (`operationsApplied > 0 AND operationsFailed > 0`), present on every return path. This makes a partially-applied batch reconcilable via `tempIdMap` instead of reading as a flat failure that prompts a duplicate-creating retry. The frontend `BulkCommitResponse` type carries the field; existing `useEditMode` rendering already derives partial state from the applied/failed counts, so behavior is unchanged and the flag is exposed for future use. (bd-5xciq, build 0002)
- **`POST /api/channels/bulk-commit` returned 504 mid-flight on large batches while the handler kept running, producing duplicates on retry (bd-ggxks, build 0001).** The endpoint was synchronous and pinned behind the 30s `ECM_REQUEST_TIMEOUT_SECONDS` middleware. A 441-op SiriusXM batch (~6 min of sequential Dispatcharr POSTs) caused the middleware to fire `504 Gateway Timeout` to the operator while the handler kept running in the background; the operator retried, each retry committed another ~30 partial channels, and Dispatcharr accumulated duplicates. Fix: bulk-commit now follows the bd-cns7j / bd-enfsy 202+poll pattern. Non-`validateOnly` `POST /api/channels/bulk-commit` returns `202 + {job_id, status: "running"}` immediately and dispatches a supervised background task; clients poll `GET /api/channels/bulk-commit/{job_id}` until the status is terminal (`completed` with the full `BulkCommitResponse` under `result`, or `failed` with an `error` message). `validateOnly` stays synchronous (200 with the response body inline) because pre-commit validation is fast and the frontend uses it for instant feedback. Frontend `bulkCommit()` and the MCP `bulk_commit_channels` / `build_channel_lineup` tools drive the new POST→poll loop transparently — their public shapes are unchanged so all three `useEditMode` call sites and existing MCP consumers keep working. Job state is in-memory with a 30-min TTL prune on every new POST; completed jobs are evicted on first read so RAM stays bounded; failed jobs persist until the TTL so operators can re-poll the error message. (bd-ggxks, build 0001)

### Added
- **Auto-creation pre-run snapshot + full revert (epic uc51o, ADR-010, builds 0018–0022).** Before each non-dry auto-creation run ECM now captures a point-in-time snapshot of every non-Dispatcharr-auto-created channel and its stream-ID assignments. The snapshot closes the revert gap that existed in the previous rollback: the old facility only undid *created* entities and surgically un-merged run-added streams; it could not restore streams removed from existing channels nor the general pre-run channel↔stream state. **Schema + capture (uc51o.2):** new `AutoCreationSnapshot` table (Alembic 0022), 1:1 FK to `AutoCreationExecution`; stores stream IDs only — never stream URLs — so Xtream-Codes credentials are never persisted in the snapshot. Capture runs in `run_pipeline` after execution-record creation and before any mutations; failure logs a WARNING and the run proceeds without a snapshot. **Restore algorithm + endpoint (uc51o.4):** `POST /api/auto-creation/executions/{id}/restore-snapshot?confirm=true` (admin-gated, `confirm` is the §D5 optimistic-overwrite acknowledgement) deletes run-created channels then full-replaces each snapshotted channel's stream set via `update_channel(streams=[ids])`; partial failures are collected and surfaced — never silent, never fatal mid-run; the endpoint is idempotent (terminal-state guard). **Retention (uc51o.3):** the `CleanupTask` prunes `auto_creation_snapshots` before VACUUM by age window (default 30 days) and count cap (default 50), whichever fires first; `ecm_auto_creation_snapshot_count` / `_bytes` observability gauges published post-prune. **Unified rollback surface (uc51o.5):** `POST /rollback` is now the single revert entry point — it probes for a snapshot and delegates to the full restore when one exists (requiring `confirm=true`), else falls back to the legacy delete-created-only path byte-compatible with pre-uc51o behaviour; `GET /executions` derives a `has_snapshot` boolean per execution in one batched `IN` query (no N+1). **MCP (uc51o.6):** new `restore_auto_creation_snapshot(execution_id, confirm=False)` tool; `confirm=False` (default) returns the optimistic-overwrite warning with channel count and snapshot timestamp before any write; `list_auto_creation_executions` now surfaces a `[snapshot]` / `[no snapshot]` marker per run. **Revert UI (uc51o.7):** "Undo this run" button in Auto-Creation execution history, gated on `has_snapshot`; shows a mandatory overwrite-warning confirm dialog with snapshot timestamp; post-revert result renders `removed_channels` / `restored_channels` / `failed_channels` — partial failures are never presented as plain success. (bd-uc51o, ADR-010, builds 0018–0022)
- **Print Channel Guide: per-group editable channel range, defaulting to each group's first/last used channel number (bd-9eyqp, build 0026).** The previous global From/To range (bd-9q9z0) and a short-lived intermediate redesign (build 0025) are replaced by per-group range inputs rendered inline in each group row. Each group's From/To defaults to that group's minimum and maximum *used* channel number (computed client-side from already-loaded data, no backend change); operators can edit each group's range independently within the modal session. The empty-slot placeholder fill (bd-w532y, build 0025 — em-dash "—" rows for sparse auto-sync ranges, toggle-on by default, 500-slot cap per group) uses each group's own range. The print button is disabled only when *no* selected group has a valid printable range; the global clamp, rangeError hint, and rangeFilteredGroups state are removed. (bd-9eyqp, bd-w532y, builds 0025–0026)
- **MCP: `set_normalization_group_enabled` tool to toggle normalization rule groups (bd-svixy, build 0024).** New MCP tool wraps the existing `PATCH /api/normalization/groups/{group_id}` endpoint to enable or disable a `NormalizationRuleGroup` by id; group ids are discoverable via the existing `list_normalization_rules` output. (bd-svixy, build 0024)
- **`custom_streams` is now a first-class Smart Sort criterion (bead ap1ud, GH #244).** Operators enable and drag operator-added custom streams in the Smart Sort priority order — exactly like `resolution` or `m3u_priority` — instead of tuning a separate M3U-row priority control. It is a binary criterion: a stream scores 1 if it is a custom stream (Dispatcharr `is_custom == true`, i.e. it belongs to the real "custom" M3U account), else 0 (negated for descending so custom streams sort first); ties among custom streams fall through to the next enabled criterion. **Default: present but disabled** (like `m3u_priority`); existing installs auto-merge it (disabled) via the frontend `mergeSortCriteria`/`ALL_SORT_CRITERIA` mechanism, so no operator action is required and saved priority orders are preserved. **Backend:** `smart_sort_streams` (and the auto-creation engine's `_smart_sort_streams`) take an optional `custom_stream_ids: set[int]` threaded through every sort surface and internal caller; each call site builds the set from the stream data it already fetches (`is_custom`), only when the criterion is active — mirroring how `m3u_priority` gates its M3U-account fetch. When `custom_stream_ids` is not supplied the criterion is inert (scores 0 everywhere), so callers degrade gracefully. **Frontend:** the criterion appears in Settings → Smart Sort Priority as a draggable, toggleable row, in the channel/group/toolbar sort dropdowns, and in the `SortMode`/`SortCriterion` types. **This supersedes the bd-4g2t1 "Custom streams" M3U-row priority control** (the row UX the PO disliked); that work never reached a release cut, so the row, its CSS, and its tests were removed in favour of this criterion. **Tests:** 5 backend criterion tests in `test_sort_criteria.py` (prober) + 5 in `test_auto_creation_engine.py` (engine) covering ranks-first-when-top, no-effect-when-disabled, pure-M3U-unaffected, inert-without-ids, and tie-fallthrough; 5 frontend tests in `SmartSortCustomStreamsCriterion.test.tsx` covering render/default-disabled/saved-enabled/toggle/auto-merge. ([bead ap1ud], GH #244)
- **Fuzzy stream→channel matching for OTA/callsign "Local" channels, built on ONE shared backend core + ONE shared name-cleaner (bead jnzst, v0.17.3-0006).** OTA locals never auto-matched because the global merge path is intentionally strict normalized-name *exact* equality (the strictness that ended a prior ~1,341 false-positive merge incident), while providers name locals inconsistently (`CITY:`/`US|`/`WI |` prefixes, `RAW`/superscript quality tags, `GREENBAY` vs `Green Bay`, channel-number prefixes). This adds a scored fuzzy path that does NOT touch the exact rule. **Core (`backend/services/dedup_matcher.py`):** the existing rapidfuzz `token_set_ratio` scorer is extended into `score_one`/`score_all` returning a `ScoredMatch` (score + `callsign_verdict` + `tvg_id_override` + `signal`), and the single cleaner `_normalize(value, mode)` gains a `LOCALS` mode (dotted/`N.N |` number-prefix strip, source/market-prefix strip, `convert_superscripts` reuse, quality-tag strip, run-together token split) while `CONSERVATIVE` (the default every existing dedup/exact caller uses) stays byte-for-byte unchanged. **Rule path (Component A):** `loose_name_match` rules can now opt into scored fuzzy via a required `min_score` (0–1, floored at `CONFIDENCE_FLOOR=0.60`) plus optional `tie_break`/`max_candidates`, scoped to the Local channel groups via the existing `target_channel_in_group` allowlist; per-merge scores + provenance are written to the journal and surfaced in the run summary. **Preview (Component B):** new no-write `GET /api/auto-creation/fuzzy-preview` (admin-gated, paginated, group-scoped, N×M-capped) returns scored `(stream_id, channel_id, score, callsign_verdict)` triples before any write. **MCP (Component C):** `match_streams_to_channels` and `fuzzy_match_stream` are repointed onto the backend core and the MCP-local scorer (`_score_match`/`_generate_variants`/`_normalize_channel`) is deleted; a new `preview_fuzzy_matches(group_ids, min_score)` tool wraps the preview endpoint; `create_auto_creation_rule`/`update_auto_creation_rule` docstrings document the fuzzy `loose_name_match` + `min_score` + `target_channel_in_group` path. **Tests:** 113 new tests incl. the tombstone property (all 4 WBAY variants match the WBAY channel and the WGBA control is excluded at every `min_score` in [0.60, 1.0]); backend suite 5187 passed/69 skipped, mcp-server suite 396 passed/37 skipped. ([bead jnzst], v0.17.3-0006)

### Security
- **Operator-only: all channel-configuration write endpoints now require admin (bd-um30y + bd-v7n9f, builds 0013–0014; auto-creation writes bd-757hc, build 0009).** ECM is an operator-only system; Dispatcharr-federated users are created `is_admin=False` by default, so authenticated non-admin principals could previously invoke destructive or bulk channel operations. Three separate gating passes closed this. **Build 0009 (bd-757hc):** 11 mutating `auto_creation.py` endpoints gated with `RequireAdminIfEnabled` (create/update/bulk-update/delete/reorder/toggle/duplicate rule, run pipeline, run rule, execution rollback, import YAML); read-only and validation endpoints stay ungated. **Build 0013 (bd-um30y):** destructive/bulk `channels.py` class gated — `clear-auto-created`, merge, bulk-merge, bulk-commit, assign-numbers, import-CSV. **Build 0014 (bd-v7n9f):** PO decision that ECM is operator-only extended the gate to all remaining channel-config writes — `create_channel`, `update_channel`, `delete_channel`, add-stream, add-streams, remove-stream, reorder-streams, and logo CRUD (create/upload/update/delete logo). Read-only GETs and preview/validation scan endpoints (`preview-csv`, `normalize-preview-batch`, `find-duplicates`) remain ungated. `RequireAdminIfEnabled` is a no-op when auth is disabled, so single-user deployments are unchanged. (bd-757hc, bd-um30y, bd-v7n9f, builds 0009/0013/0014)
- **SSRF denylist on media-server saved-URL test-connection endpoints (bd-fbc50, build 0024).** `_sanitize_base_url` in `routers/settings.py` already blocked non-`http`/`https` schemes but still permitted loopback and link-local hosts, leaving an admin-gated SSRF surface on the Emby/Plex/Jellyfin "Test Connection" endpoints. Two new stdlib-only helpers (`ipaddress` + `socket`, no regex): **`_ip_is_blocked`** denies loopback (`127.0.0.0/8`, `::1`), link-local IPv4 (`169.254.0.0/16`, including the AWS/GCP `169.254.169.254` metadata endpoint), link-local IPv6 (`fe80::/10`), and IPv4-mapped IPv6 unwrapping (`::ffff:127.x.x.x`, `::ffff:169.254.x.x`); RFC 1918 private ranges are intentionally left reachable (Plex/Emby/Jellyfin run on the operator's LAN). **`_host_is_blocked`** applies the IP check to literal IPs, blocks the `localhost` alias by name, and performs best-effort hostname resolution so a hostname resolving to a blocked IP is also caught; resolution failures do not block (offline LAN servers stay testable). Denied hosts return the same `{ok: false, error: <msg>}` envelope as the scheme-block path. (bd-fbc50, build 0024)
- **Reintroduced fuzzy matching is gated so it cannot recreate the ~1,341 false-positive merge incident (bead jnzst).** The admission decision is a single shared chokepoint (`dedup_matcher.is_admissible`) that the rule executor, the preview endpoint, and — transitively — both MCP write tools all funnel through, so no consumer can apply a score-only policy and re-admit an incident-class false positive. Invariants enforced + test-pinned: **callsign hard-reject** (when both names parse a callsign and they differ, the pair is rejected before any threshold, beating `min_score` and the tvg_id override); **callsign required on both sides by default** for Locals fuzzy (no-callsign pairs admitted only via explicit opt-in and only at score ≥ 0.90); **refuse unscoped scored fuzzy** (schema validation rejects a `min_score` rule without a non-empty `target_channel_in_group`; legacy `loose_name_match` rules without `min_score` are unaffected); **tvg_id-callsign override fails closed** under a name-callsign conflict; **mandatory dry-run** with a test asserting the preview path performs zero writes; **journaled scores + provenance** (score, effective threshold, signal fired, both parsed callsigns, rule id, allowlist) for forensic reconstruction; and **journal-driven surgical rollback** that removes only the stream-ids a fuzzy merge added (preserving edits made after the merge), falling back to snapshot-restore only when journal data is missing. The new preview endpoint is `RequireAdminIfEnabled`-gated with `group_ids` validation/caps to bound the N×M scoring surface. **ReDoS hardening** on the `LOCALS` cleaner: input is length-capped before any regex and whitespace is collapsed once up front so the source-prefix regex is linear-time (the prior pattern was O(n²) on whitespace-padded, attacker-controllable M3U names). The global exact-match rule and the `match_by` no-op are untouched. ([bead jnzst])

Also raises `CleanupTask.journal_days` default from `30` → `90` to align with `journal.purge_old_entries`'s existing 90-day default — bulk operations now amplify journal row volume N-fold, and the inconsistent retention default would have masked unbounded table growth. CleanupTask was already wired into the scheduler; no integration changes required (PR #133, bd-dmu8w).
- Stats tab no longer crashes with React error #185 (Maximum update depth exceeded) on every load. Recharts 3.x bundles `react-redux` + `@reduxjs/toolkit` for internal state; under React 19's stricter concurrent rendering, the chart's `YAxis` → `RenderedTicksReporter` `useEffect` re-dispatched `setRenderedTicks` with a fresh `ticks` array reference on every render, which forced a re-render that re-ran the effect, looping until React aborted with #185 inside the ErrorBoundary scoped to the Stats tab. The trigger was the React 18.3.1 → 19.2.5 bump in `ca6e5019` (bd-in620, 2026-04-24); the recharts 3.7.0 → 3.8.1 bump in `62ea5c5f` (2026-04-16) seeded `RenderedTicksReporter` itself, but the loop only manifested under React 19. Pin `recharts` to `2.15.4` — the latest 2.x line, declares React 19 support in peerDeps, and pre-dates the redux refactor entirely. Our chart usage (`LineChart`/`AreaChart`/`BarChart` + `XAxis`/`YAxis` + `Tooltip` + `ReferenceLine` + `ResponsiveContainer`) is all stable across the 2.x→3.x boundary; tsc clean and 110 stats panel tests pass against 2.15.4 (bd-a7l1z).

### Security
- `backend/routers/backup.py` — canonicalize-and-verify (`resolve()` + `relative_to()`) applied to `download_saved_backup` and `delete_saved_backup` as defense-in-depth alongside the existing `_BACKUP_FILENAME_RE` guard. Closes CodeQL py/path-injection alerts 1416-1419 (CWE-22/23/36/73/99). Pattern mirrors the zip-restore remediation in the same file. New tests cover traversal, absolute paths, symlink-escape, and null bytes (PR #98, bd-0a1pr).
- `backend/cloud_storage/onedrive_adapter.py` — Pydantic + adapter-level validators on `tenant_id` (GUID or verified domain) and `drive_id` (base64url-style) prevent SSRF via Microsoft Graph URL interpolation. Closes CodeQL CRITICAL py/partial-ssrf alerts 1361, 1362 (CWE-918). New tests at `backend/tests/test_cloud_storage.py` cover validator unit coverage + HTTP 422 at the cloud-target API (PR #101, bd-zbt74).
- `backend/auto_creation_schema.py` — three write-time `re.compile(<user_input>)` sites (condition regex validation, set_variable pattern validation, name_transform_pattern validation) now route through `safe_regex.compile`, which enforces a length cap and uniform compile-error surface. User-controlled regex from auto-creation rule definitions can no longer pin a worker via crafted ReDoS patterns. The bd-91mcq auto-creation bulk merges expanded request volume through these paths; this hardening closes the exposure window. Removes the three `# nosemgrep: no-bare-re-on-dynamic-pattern` annotations + their `TODO(enhancedchannelmanager-ltjyx)` markers. Backward-compatible: error message substrings (`"Invalid regex"`, `"Invalid name_transform_pattern"`) preserved for existing test/UI assertions. New `TestSafeRegexMigrationWriteTimeValidation` (10 tests) covers oversize-pattern rejection at all three sites + boundary-at-cap acceptance (PR #136, bd-ltjyx).
- `backend/routers/m3u_digest.py` — two write-time `re.compile(<user_input>)` sites validating `exclude_group_patterns` and `exclude_stream_patterns` from request bodies now route through `safe_regex.compile`. Same ReDoS class as bd-ltjyx, different surface (M3U digest endpoint instead of auto-creation rule endpoint). Removes the two `# nosemgrep` annotations. New tests in `TestUpdateDigestSettings` cover oversize-pattern rejection on both fields plus a `TestRouterUsesSafeRegex` source-level revert guard (PR #135, bd-3u6p0).
- Eight CodeQL py/stack-trace-exposure HIGH alerts (1412-1415, 1350-1353) remediated across `backend/routers/{backup,channels,export,health,settings}.py` + `backend/cloud_storage/`. Pattern: `logger.exception(...)` for full trace correlated by `X-Request-ID` + return only the exception class name (`type(e).__name__`) in the API response — never `str(e)` (which can include connection strings, file paths, or credentials). For `ImportError` paths in cloud_storage adapters, `e.name` (the missing module name) is used so the response stays useful without leaking interpreter paths. **Material risk closed**: alert 1414 in `health.py` — `/api/health/ready` is in `AUTH_EXEMPT_PATHS`, meaning DBAPI exception messages were echoed unauthenticated; this PR closes that. ADR-005 Phase 1 disallows "won't fix" dismissal so every open stack-trace alert needed a real fix. Six new sanitization tests + 1 updated, each asserting both the positive contract (response equals exception class) and the negative contract (the secret-bearing message body MUST NOT appear in the response) (PR #160, bd-m8i9q).
- `backend/export_manager.py` + `backend/routers/export.py` — defense-in-depth canonicalize-and-verify backstop for path traversal in the M3U/XMLTV export download paths. New `_safe_export_path(profile_id, *parts)` helper resolves and verifies containment under `EXPORTS_DIR.resolve()` via `Path.relative_to()`, raising `ExportPathError` on escape. Wired into `ExportManager.get_export_path` and `ExportManager.cleanup` (cleanup short-circuits before `rmtree` on escape). Also re-verifies path containment in `download_m3u`/`download_xmltv` before serving. CodeQL py/path-injection alerts 1354-1359 were already dismissed as false-positive (FastAPI int path-param + Pydantic `FILENAME_RE` allowlist make traversal unreachable upstream), but per ADR-005 sequencing 2 and the bd-0a1pr precedent the property is now guaranteed at the sink rather than depending on caller hygiene. New `TestExportPathInjection` (9 tests) mirrors `TestSavedBackupsPathInjection` from bd-0a1pr — traversal payloads, absolute paths, null-byte, backslash, cleanup sentinel-file regression, symlink-escape (PR #159, bd-h5rfv).

## [0.15.1] — 2026-03-31

### Added
- Login rate limiting — 5 attempts per minute per IP via slowapi on both local and Dispatcharr login endpoints.
- Security headers: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`.
- Client IP in login-failure logs (includes `X-Forwarded-For` for forensics).

### Changed
- **Password policy now follows NIST 800-63B** — dropped composition rules (uppercase/lowercase/number), replaced the 33-word list with the 10k common-passwords list, uniform 8-character minimum for all users including admin-created.
- CORS tightened — explicit method and header allow-lists instead of wildcards.

### Fixed
- EPG matching: channel names with a number prefix (e.g. `535 | ESPN`) were normalizing to `535espn` instead of `espn`, causing zero matches against EPG data.

### Security
- Injection / SSRF (OWASP A03/A10):
  - ffmpeg protocol allow-list on all invocations — blocks `file://`, `data://`, `concat:` and other dangerous protocols.
  - URL-scheme validation at input time on M3U, Xtream Codes, and EPG source endpoints — only `http://` and `https://` allowed.
  - Zip backup path canonicalization — defense-in-depth `resolve()` check alongside existing traversal guards.
- Logging hardening (OWASP A09):
  - 500-response scrubbing — global handler returns generic `Internal server error` to clients; real error stays in server logs.
  - Validation-error log redaction — `Authorization` / `Cookie` headers and auth-endpoint request bodies redacted from logs.

## [0.15.0] — 2026-03-29

### Added
- **Export & Publish** — generate M3U/XMLTV playlists from channel profiles and publish to cloud targets (S3, WebDAV, etc.) on a cron schedule. Includes channel selector, playlist preview, cloud-target management, and publish history.
- **Low-FPS detection** — streams below a configurable threshold (5/10/15/20 FPS) are flagged with an amber icon and deprioritized in Smart Sort. Zero-overhead, always-on, configurable in Settings → Maintenance.
- **Black-screen detection** — optional ffmpeg `signalstats` check after each probe flags dark/blank streams with a purple icon. Configurable sample duration (3–30s) in Settings → Maintenance.
- **Normalize Names engine** — tag-based rules engine for cleaning up stream names during bulk channel creation. YAML import/export, edit/revert controls, drag-and-drop priority ordering.
- **Backup & Restore** — full configuration backup/restore from Settings, with restore option during the first-run setup wizard.
- **Merge Channels** — combine two or more channels into one, consolidating their streams.
- Auto-creation enhancements — EPG logo-source action, Probe Streams action, Set Channel Profile action; Smart Sort option in rule sort dropdown; rule selection in Auto-Create schedule; separate stream sort from channel sort per rule.
- PUID/PGID support for Docker container user identity.
- TV Guide print view.
- JWT authentication in Swagger UI with `/swagger` redirect.
- Debug bundle for troubleshooting auth issues.

### Changed
- Server-side migration of EPG matching, stream normalization, and edit consolidation (previously client-side).
- Settings UI consistency — compact dropdowns, unified admin section CSS, proper field ordering.
- Scoped reprobe to last scheduled probe's channel groups.
- Capped Dispatcharr HTTP client connection pool.
- All GitHub Actions updated to Node.js 24-compatible versions.
- Migrated 161 `console.log` call sites to the structured logger.

### Fixed
- Persistent 503 when stream prober not initialized — prober now self-heals and auto-creates.
- `assign_logo` from EPG and duplicate rule priorities.
- Radio buttons, undefined CSS variables, and card backgrounds in admin tabs.
- Push-down renumbering, menu overflow, task-card grid.

### Removed
- ~2,000+ lines of dead code across backend and frontend, including duplicate `formatDate` implementations.

### Security
- Secured backup endpoints; improved token handling.
- Fixed npm audit vulnerabilities in `brace-expansion`, `flatted`, `picomatch`.
